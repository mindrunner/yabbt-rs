# Threat Model

## Current Scope

The current CLI can create Bitwarden/Vaultwarden backups through the official `bw` CLI, inspect and verify encrypted archives, diff a live `bw` vault against an archive, restore into `bw` with dry-run/apply support, and run a one-way `sync` between two named `bw` profiles. KeePass (.kdbx) databases work as a restore/sync target and as a backup/diff/sync source (see "KeePass Databases" below). Restore apply is conservative by default: it creates missing data, optionally updates matched changed items with `--update-existing`, maintains restore-map idempotency unless opted out, and does not delete target-only data unless `--prune` is explicitly passed. `rbw` is not supported.

## Assets

Archives contain password-manager secrets, notes, TOTP seeds, metadata, and attachment contents. Treat every archive payload and temporary plaintext file as sensitive.

## Current Archive Implementation

The current implementation writes a versioned tar payload, compresses it with `zstd`, and encrypts it using passphrase-based `age` encryption.

Archive writes go to a randomly named, owner-only (mode 0600, created exclusively) temp file in the `--out` directory, which is fsynced and then published under the final name; the directory is fsynced after the publish. An interrupted write therefore never leaves a partial archive at `--out`, a stale temp file from a crashed run never blocks the next write, and nothing can pre-plant a symlink at a predictable temp name. Without `--overwrite`, the publish itself refuses to replace an existing file (`renameat2(RENAME_NOREPLACE)` on Linux, hard link plus unlink elsewhere), so a file that appears at `--out` after the up-front existence check — while the export runs — is never silently replaced; the run fails with exit code 2 and discards the new archive. On a filesystem that supports neither (some FUSE mounts), the no-clobber publish fails closed with an error saying so and suggesting `--overwrite` or a local filesystem. A directory fsync that the filesystem rejects as unsupported (EINVAL/ENOTSUP) after the archive is already published is reported as a warning, not as a failed write.

Decoding an archive (for `inspect`/`verify`/`diff`/`restore`) is bounded: the decompressed payload is capped at a fixed size so a zstd decompression bomb cannot exhaust memory, the tar entry count is capped, and duplicate `manifest.json`/`vault.json` entries are rejected rather than last-wins. `restore` opens and verifies the archive from a single decrypt+decode pass, closing the previous time-of-check/time-of-use gap where the file was read twice and could be swapped between the open and the verify.

Verification decrypts and decompresses the archive, parses `manifest.json`, validates `vault.json`, confirms attachment entries, and compares a SHA-256 digest over the vault JSON and attachment payloads.

`verify` applies semantic validation: the backup report must be complete, every attachment reference must have a matching payload, every stored attachment payload must be referenced, attachment sizes must match, and non-empty attachment SHA-256 values must match the payload bytes.

`inspect` is informational. It validates that the archive is readable and prints safe counts, but it does not fail solely because the backup report is marked incomplete.

A `bw` backup without `--organization-id` covers the personal vault only. Organization items the account can see but the export lacks mark the report incomplete (`org-items-not-exported`), so a partial backup is never silently treated as a full copy. `--personal-only` (`backup`/`sync` with a `bw` source) is the explicit opt-out: the same items are recorded as an informational `org-items-excluded-by-scope` warning and the report stays complete. Both warnings carry only a count — no item names, item IDs, or organization IDs — and so does the stderr notice `backup` and `sync` print after writing an archive that has warnings (completeness plus warning codes and counts).

## Passphrase Handling

Backup reads the archive passphrase from `--passphrase-env <ENV>`. This avoids command-line argument history but still exposes the secret to the process environment. Future versions should support file-descriptor or interactive secret input.

Backup refuses weak archive passphrases by default. The current policy rejects empty, short, common, repeated-character, and low-diversity values, while accepting long random-word passphrases. `backup --yolo` is an explicit override for testing or knowingly weak archives.

Clear passphrase environment variables after backup on shared machines.

## Bitwarden Profiles and Sessions

Named profiles live under `$XDG_DATA_HOME/yabbt/bw-profiles/<name>` (default `~/.local/share/yabbt/bw-profiles/<name>`), created with mode 0700, and are used as `BITWARDENCLI_APPDATA_DIR`. Each profile directory contains the Bitwarden CLI's local state for that account — the same sensitivity as `~/.config/Bitwarden CLI`. Treat profile directories as sensitive and remove them with `bw logout` (inside the profile) or by deleting the directory when an account is retired.

Profile authentication is delegated to `bw` itself: `yabbt bw-login` and the interactive unlock spawn `bw` with the terminal attached, so the master password is typed directly into `bw` and never passes through yabbt. The captured session key is held in process memory only and handed to `bw` child processes via the `BW_SESSION` environment variable; it is never written to disk, argv, or logs. Note that on a successful `bw login`, `bw` itself prints an `export BW_SESSION=...` line to stdout (inherited from the terminal); yabbt does not use that value and warns the operator that it landed in their scrollback. Command requests redact environment values in debug output. In profile mode `BITWARDENCLI_APPDATA_DIR` and `BW_SESSION` are always set by yabbt and never inherited, so another account's ambient session or data directory cannot cross-contaminate the profile; see "`bw` Child Environment" below for the rest of the environment.

Restore and sync write item, folder, and restore-map payloads to `bw` on stdin (`bw create item` / `bw edit item` with the positional argument omitted), never on argv, so vault secrets in those payloads are not exposed through `/proc/<pid>/cmdline`, `ps`, or process-accounting logs. Object identifiers passed to `bw` (item/folder/attachment IDs) are validated against an allowed character set before use so a hostile server or poisoned restore map cannot smuggle a `bw` option in an ID position. IDs returned by `bw create item`/`bw create folder` are validated the same way before yabbt stores or reuses them, and temporary attachment paths are built from local job indices only — never from a backend-supplied ID — so a hostile server returning an ID like `/home/u/.config/x` cannot make yabbt write plaintext attachment bytes outside its private temporary directory.

## Sync

`sync` composes backup, archive verification, and restore across two distinct backends (bw profiles and/or a KeePass database) and is dry-run by default. The source side is read-only by construction: only the target adapter is handed to the restore apply orchestration, so no code path can mutate the source. With two bw profiles, source and target must resolve to different directories; keepass-to-keepass sync is rejected. All restore guardrails (blockers, strict verification before apply, prune being opt-in and trash-first, the mass-delete guard) apply unchanged, and sync output follows the same counts-and-IDs-only rules as backup and restore. Sync stages the new archive in a temp file, reads it back, and verifies it strictly before it touches `--out`: only a verified — and therefore complete — archive is published, and it is published before planning (even on a dry run) so the run doubles as a backup. An incomplete or unverifiable export is discarded, leaves `--out` untouched even with `--overwrite`, and blocks the plan (exit code 3). Because a verified archive of a wiped or compromised source can still be published, `backup` and `sync` refuse to replace an existing `--out` without `--overwrite`, so such a run cannot silently replace the last good backup; sync also refuses an `--out` that names the KeePass database, one of its timestamped `<kdbx>.<UTC timestamp>.bak` copies, or its temp file. A blocked plan exits with code 3, including on dry run, so automation does not proceed to `--apply`.

## KeePass Databases

The KeePass backend reads the database passphrase from `--keepass-passphrase-env <ENV>` — the same exposure trade-offs as the archive passphrase apply, and the passphrase is held in process memory for the run. Keyfile support is a documented follow-up.

There is no weak-passphrase policy on a *pre-existing* database (it keeps whatever passphrase it has), but creating a brand-new database through `restore`/`sync` now enforces the same passphrase-strength policy as `backup`, with `--yolo` as the explicit override. The keepass passphrase is held in a zeroize-on-drop buffer for the duration of the run.

Writes use the `keepass` crate's experimental KDBX4 writer, which re-serializes the file from its parsed object model: KDBX data the crate does not model (plugin data, KeeShare configuration, custom icons) can be silently dropped on rewrite, while entries, groups, fields, TOTP, tags, and attachments round-trip. Mitigations: before the first write of each run to a pre-existing file, yabbt copies it to a new `<file>.<UTC timestamp>.bak` and prints a notice (paths only); an existing `.bak` is never overwritten, so the pre-yabbt original survives later runs. Restore mutations only change the in-memory database; the apply writes the file once at the end (and once more before the best-effort restore-map write if the apply failed part-way). Edits that would leave an entry identical and restore-map chunks whose content is unchanged are not applied, so a run that changes nothing never rewrites the file or makes a `.bak` copy. Right before each save, yabbt re-hashes the file and refuses to write if it differs from what yabbt last read or wrote (another program, e.g. KeePassXC, saved it during the run) or if a file appeared where yabbt was about to create one: nothing is written, the run's pending changes are discarded, and the error asks for a re-run. The check cannot catch a save landing in the few milliseconds between it and the rename. Every save writes a sibling temp file, re-opens it, compares each entry's attachments (names and SHA-256, current and history versions) with the in-memory state, and only then atomically renames it, so a crash never leaves a partial database and a writer bug that misplaces attachments aborts the save with the original untouched. When a save fails, the unsaved changes are discarded from memory (the file is re-read), the error says nothing was written, and the apply summary reports only what an earlier save persisted. The temp file and `.bak` copies are created owner-only (mode 0600) with create-new semantics, so the atomic rename never downgrades a hardened database's permissions and a predictable sibling name in a shared directory cannot be redirected through a pre-planted symlink. Each `.bak` copy is a full encrypted database under the passphrase it had at the time — treat them with the same sensitivity as the original and clean them up when no longer needed.

The crate's KDBX4 writer mis-numbered attachment references after any binary was removed from the pool (keepass 0.13 to 0.15.4; 0.15.5 renumbers the pool on save), and its removal helpers drop binaries still shared by other entries or history versions. yabbt therefore performs attachment removals itself: current-version references are detached and re-added so the pool stays dense, binaries referenced from entry history keep their pool position, and a history version whose attachments are a subset of its entry's current ones is rebuilt from the current version (keeping the version's own fields, times, tags, and colours) when its old positions would leave an unfillable gap. The plan for each removal is computed before anything is touched; a removal that would still lose a file only entry history needs (an attachment kept in the same entry's history, or a history-only file below an unfillable gap) is refused with an error naming the entry, leaving the database unchanged. Restore apply skips such a refused prune of an attachment instead of aborting: the attachment stays, the summary reports it under `attachments_delete_skipped`, stderr names only the target item ID, and the run succeeds. A refused permanent entry delete (`--prune-permanent`) still aborts the apply. A removal that fails half-way poisons the in-memory database so it can never be saved. yabbt identifies KeePass attachments by a hash of the entry UUID and attachment name, never by pool position, so planned deletes and post-apply verification keep pointing at the right attachment while the pool is renumbered.

Secrets written into the kdbx (passwords, TOTP seeds, hidden custom fields, the verbatim item payload in the `yabbt.bitwarden_raw` field, attachment bytes) are stored as KDBX protected values. Non-permanent prune moves entries to the database's Recycle Bin group rather than deleting them; `--prune-permanent` removes them outright. The crate's group removal is recursive and bypasses the Recycle Bin, so yabbt only ever removes a group that is already empty, and prune never schedules the parent of a group it keeps (nested groups are folders named `Parent/Child`). Entries anywhere inside the Recycle Bin subtree are treated as trashed and never read as live items. Newly created databases use Argon2id with 64 MiB of memory, 10 iterations and parallelism 2 (the crate default, Argon2d with 1 MiB, is far too cheap); pre-existing databases keep their own KDF settings. The `YABBT_KEEPASS_KDF=insecure-fast` environment hook weakens the key derivation of newly created databases; it is compiled out of release builds (only present in test/debug builds) and prints a loud warning when it takes effect, so it cannot silently weaken real data.

The `yabbt.bitwarden_raw` field on entries authored outside yabbt is untrusted input. Rendering a kdbx entry coerces malformed nested JSON in that field rather than indexing into it, so a hostile or corrupted database cannot crash yabbt during scan/export.

## Logging

Default output must not include passwords, TOTP seeds, notes, attachment bytes, or unredacted command output. Reports may include object counts, backend versions, IDs, and redacted diagnostics. Current `bw` command failures include redacted stderr only.

`inspect` and `verify` intentionally print only safe archive metadata and aggregate counts. They must not print item names, folder names, notes, usernames, passwords, TOTP values, custom field values, attachment names, or attachment bytes.

`diff` intentionally prints counts and item IDs only. It must not print item names, folder names, notes, usernames, passwords, TOTP values, custom field values, attachment names, or attachment bytes.

`bw` command failures surface a sanitized form of the backend's stderr: whitespace is collapsed, long opaque tokens (the shape of base64 payloads or session keys) are replaced with `<redacted>`, and the message is length-bounded, so a verbose or hostile backend cannot dump large or secret-bearing output to the terminal. Reading a passphrase from an environment variable reports only whether the variable is missing or not valid UTF-8 — never the value itself. Internal structs that carry secrets (vault items and their fields, command output bytes, attachment payloads, the decrypted keepass database) have hand-written `Debug` implementations that redact the sensitive parts, so an accidental debug format cannot leak them.

`restore --dry-run` intentionally prints a mutation plan with counts, blockers, and item/folder IDs only. It must not print item names, folder names, notes, usernames, passwords, TOTP values, custom field values, attachment names, attachment bytes, or attachment filenames. For the `bw` target, dry-run performs a read-only target scan through the official `bw` CLI so folder create counts and item create/update/unchanged counts are target-aware. It must not mutate any target vault.

`restore --apply` is create-only by default. It recomputes the plan, requires strict archive verification, creates missing target folders by exact folder-name match, rewrites restored item folder IDs to target-vault folder IDs, creates only missing items, uploads attachments only for newly created items, skips updates, and never deletes target-only folders or items unless `--prune` is explicitly passed. Output must remain count-based and secret-safe.

`restore --apply --prune` is destructive mirror reconciliation. It deletes target-only attachments, target-only items, and target-only folders after a fresh plan. A target attachment of a matched item is only pruned on its own when all of that item's archive attachments are already on the target; otherwise (changed content, a renamed file) the delete is tied to the item update and runs only with `--update-existing`, after the replacement upload succeeded, so prune never leaves an item without either version. On a KeePass target, whose apply is saved in one commit, a same-name replacement removes the old version right before the upload so the new version keeps the file name; both land in the same save, and if the upload fails the whole run is discarded and nothing is written. Target-only item deletion sends items to Bitwarden Trash by default; `--prune-permanent` passes `--permanent` and is irreversible. Prune output must print counts and IDs only. Prune must stop before mutation if restore planning has blockers or ambiguous matches. A mass-delete guard blocks the plan when the archive contains no items, or when prune would delete more than half of the target's items and more than 10 of them, unless `--allow-mass-delete` is passed, so a wiped source or the wrong archive cannot empty a mirror in one run.

Bitwarden organization and collection completeness is deferred to a later dedicated pass. Until then, restore must keep guardrails so source organization IDs and collection IDs are not replayed blindly. Collection-scoped archive items remain blocked until collection mapping exists. Blockers report only affected archive item IDs and a generic reason; they must not print source organization IDs, collection IDs, collection names, or item secrets. `restore --apply` must stop before any target mutation when a blocker is present.

`restore --apply --update-existing` also updates changed target items that were matched by restore map, per-item marker, original ID, or unique normalized fingerprint. It uses `bw edit item <id> <encodedJson>` and must not update ambiguous matches. For existing matched items, yabbt uploads archive attachments that are missing on the target item. Attachments are paired one-to-one by SHA-256 content when both sides carry checksums (archives and KeePass targets do), regardless of file name, so changed bytes under the same name count as a change; they fall back to the file name alone (no size or content comparison) when the target carries no checksum (`bw` listings). An item counts as changed because of its attachments only when an archive attachment is missing on the target; target-only attachments are left to `--prune`. Without `--prune` it never deletes target-only items or target-only attachments, and it does not overwrite existing attachments.

`restore --apply --verify-after` fetches each newly created target item ID returned by `bw create item` and each updated target item ID passed to `bw edit item` using `bw get item <id>`, then verifies each uploaded attachment by looking it up by file name on the fetched item, downloading it, and comparing the SHA-256 of the downloaded bytes with the archived checksum. With `--prune`, it verifies deleted item, attachment, and folder IDs are absent from fresh target metadata. It prints only verification counts. It must not print fetched item JSON, item secrets, attachment names, attachment bytes, folder names, or deleted-object names. This confirms created and updated items and uploaded attachments are visible after mutation, and that pruned objects are no longer visible, but it does not make repeated restore idempotent by itself.

`restore --apply` writes or updates one yabbt-managed secure note named `yabbt restore map - do not edit` in the target vault by default. The note contains a hidden `yabbt.restore_map` field with JSON mapping archive item IDs to Bitwarden-assigned target item IDs and source fingerprints. The map is updated for newly created items and for archive items that already matched an existing target item; a chunk whose content would not change is not rewritten. If a map entry points to a missing target item, planning reports only the stale source item ID and apply removes that stale entry when rewriting the map. This avoids per-item metadata, but the map item name and hidden field name are visible to vault owners, exports, CLI access, and anyone with decrypted vault access. Restore planning excludes this map item from normal target counts. `--no-restore-map` opts out of creating or updating this item and accepts weaker duplicate prevention.

`restore --apply --mark-restored` writes hidden custom fields into newly created Bitwarden items: `yabbt.source_item_id`, `yabbt.source_fingerprint`, and `yabbt.archive_version`. These fields are hidden in Bitwarden's UI but are still visible to vault owners, exports, CLI access, and anyone with decrypted vault access. Restore planning uses these markers to avoid duplicate creates on later runs.

The restore map and the `yabbt.source_item_id` markers live in vault data that anyone with vault access can edit, yet they decide which target item a match (and therefore an `--update-existing` overwrite or a `--prune` delete) acts on. Known gap: map entries and markers are currently trusted as-is, so anyone who can edit the target vault can point an archive item at an unrelated victim item and steer an `--update-existing` overwrite or a `--prune` delete onto it. Comparing the stored `yabbt.source_fingerprint` is not a defense — it is stored in plain text in the same writable vault and changes whenever the source item is legitimately edited. Closing this needs a keyed MAC over each mapping with a secret not stored in the vault; until then, only point yabbt at target vaults whose other writers you trust.

If no restore-map, per-item marker, or ID match exists, restore planning falls back to an exact normalized item fingerprint that excludes target-assigned item IDs and volatile backend metadata. The same fingerprint drives change detection and covers the raw item payload (card, identity, SSH key, passkey data), so tampering with data outside the thin item model on the target is detected and repaired by `--update-existing`; password history is deliberately excluded because Bitwarden rewrites it on every password edit. Each target item is bound to at most one archive item, and identity matches (map, marker, original ID) are resolved before the fingerprint fallback. It only auto-matches when exactly one target item has that fingerprint. Ambiguous fingerprint matches are reported by archive item ID only and are not guessed silently.

Restore apply is not fully idempotent for items created with `--no-restore-map` and without `--mark-restored` if the item was edited later or if duplicate-looking items exist. Repeated apply runs may create duplicates for untracked restored items until additional natural-key matching is implemented. See `docs/design/restore-idempotency.md`.

## Temporary Data

The `bw` adapter downloads attachments into a temporary directory before adding them to the encrypted archive. Restore also writes attachment bytes into a temporary directory because `bw create attachment --file <path>` requires a filesystem path. These directories are created owner-only (mode 0700) and the plaintext attachment files yabbt writes are created mode 0600, so other local users cannot read them even though the directory lives under the shared system temp location. The temporary directory is removed when the operation completes. If the process is killed, the OS temporary directory may contain plaintext attachment bytes until cleanup.

Later stages should reduce or harden this plaintext attachment exposure. Options to evaluate include using an OS-backed memory filesystem when available, setting stricter temporary-directory permissions, best-effort cleanup reporting on failure, and investigating whether future Bitwarden APIs can stream attachment data without writing plaintext files. The archive vault JSON and decrypted archive payload should continue to stay in memory and should not be written as standalone plaintext files.

## Backend CLI Risks

The `bw` adapter executes the `bw` binary found on `PATH` and passes arguments without shell interpolation. Users should ensure `bw` is the official Bitwarden CLI and that `BW_SESSION` or equivalent authentication state is scoped to the intended account/server.

### `bw` Child Environment

yabbt relies on `bw`'s exit status and stdout shape, but `bw` reads environment variables that change both: with `BW_CLEANEXIT` set, failed commands exit 0 (a failed `edit`/`create`/`delete`/`sync` would look successful and restore would report success with nothing applied); `BW_RESPONSE`, `BW_QUIET`, `BW_RAW`, and `BW_PRETTY` change what is printed; `NODE_TLS_REJECT_UNAUTHORIZED=0` disables certificate verification and `NODE_OPTIONS` can inject code into the Node runtime. Every `bw` invocation — adapter calls and the interactive `bw-login`/unlock path alike — therefore starts from a cleared environment plus an allowlist:

- `PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LANGUAGE`, `LC_*`, `TZ`, `TMPDIR`, `TERM`, `XDG_*` (bw's default data directory on Linux), and the minimum Windows variables Node needs.
- Proxy settings: `http_proxy`/`HTTP_PROXY`, `https_proxy`/`HTTPS_PROXY`, `no_proxy`/`NO_PROXY`, `all_proxy`/`ALL_PROXY`.
- `NODE_EXTRA_CA_CERTS`, kept so self-hosted servers behind a private CA keep working. It only adds trust anchors; it cannot disable verification. An attacker who can set it can also replace `bw` on `PATH`, so stripping it would buy nothing.
- Account selection: without a profile, the user's `BW_SESSION` and `BITWARDENCLI_APPDATA_DIR` pass through (the documented `export BW_SESSION=...` workflow). With `--bw-profile`, both are set by yabbt and the ambient values are dropped.

`BW_CLIENTID`, `BW_CLIENTSECRET`, `BW_PASSWORD`, the archive/keepass passphrase variables, and anything else not listed are not passed. yabbt sets `BW_NOINTERACTION=true` itself for non-interactive adapter calls; the parent's value is ignored. `BW_CLEANEXIT`, `BW_RESPONSE`, `BW_QUIET`, `BW_PRETTY`, `BW_RAW`, `BW_NOINTERACTION`, `NODE_TLS_REJECT_UNAUTHORIZED`, and `NODE_OPTIONS` are never inherited.

`YABBT_BW_ENV_PASSTHROUGH` (comma-separated names; a trailing `*` matches a prefix) is an explicit escape hatch for setups that need an extra variable. It cannot re-admit the never-inherited variables above, nor the profile-managed `BW_SESSION`/`BITWARDENCLI_APPDATA_DIR` in profile mode. The test suite uses it to steer its fake `bw` scripts.

For self-hosted Bitwarden or Vaultwarden, `--server-url` runs `bw config server <url>` before export. Confirm the configured target before backing up sensitive data.

## Dependencies

Cryptographic and parsing dependencies are pinned in `Cargo.lock`. The only known advisory at the time of writing is `RUSTSEC-2026-0173` (`proc-macro-error2` unmaintained), a build-time-only transitive dependency pulled in through `age`'s localization stack; it is not part of the runtime attack surface and is tracked for resolution via an `age` upgrade. Note that `cargo audit` may fail locally on an older advisory-db with `unsupported CVSS version: 4.0`; upgrade `cargo-audit` to scan.

## Live Integration Tests

Live integration tests must be opt-in through environment variables and must never target a real personal vault by default.
